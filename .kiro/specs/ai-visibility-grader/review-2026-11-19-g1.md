## V55. When both limits are full, the visitor gets the wrong message (Requirement 25.4)
server/routes/grade.js 103-108 shows the network message only when the network is full and the address is not. Requirement 25.4 says every check over the network limit gets its own message.

The reviewer ran this case:
1. One address runs 5 checks.
2. 15 other addresses on the same /24 fill the network.
3. The first address tries again 10 minutes later.

It got "a lot of checks from your address… try again a little later" with a `Retry-After` of almost 24 hours.

- Show the network message whenever the network rule is full: `networkFull ? tooManyNetwork(...) : tooMany(...)`.
- The address peek is no longer needed for the message.
- Add a test with both limits full that expects the network message.

## V56. One IPv6 machine can wipe its own network count (Requirement 25.4)
The rate limiter keeps at most 10,000 keys and drops the least recently used (server/lib/rate-limiter.js 11 and 71-82). The `/mcp` limit keys on each exact address.

The reviewer ran this case:
1. A /64 reached its network limit (set to 2 for the test).
2. It sent 10,050 requests to `/mcp`, each from a different address in the same /64. That took 6 seconds.
3. The `grade-network:` key was dropped, and the next check went through.

That defeats the network limit for IPv6, which is exactly the address-switching it exists to stop. Pick one fix:
- **(preferred)** Give the three new-check rules (`grade`, `grade-day`, `grade-network`) their own limiter, used only by `POST /grade` (`ctx.gradeLimiter`, injectable as `deps.gradeLimiter`, made with the same clock). Only a check that starts creates those keys, so their number stays small, and no other route can push them out.
- Or never drop `grade-network:` keys while they still hold counts inside their window.

Either way, existing tests must keep passing unchanged. If one reads these keys from `ctx.rateLimiter`, list it before changing anything.

Test: fill a /64's network limit, then send more than 10,000 `/mcp` requests from different addresses in that /64. The next check from that /64 is still refused.
