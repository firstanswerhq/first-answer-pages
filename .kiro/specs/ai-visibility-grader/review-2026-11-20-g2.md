## V59. A bad token can get through when Cloudflare answers with a 4xx status (must fix)
turnstile.js line 42 treats any status outside 200-299 as `unreachable`, so the check is let through. That happens even when the body says `{"success":false,"error-codes":["invalid-input-response"]}`; the reviewer's 400 case did exactly that. Cloudflare doesn't document which status comes with a bad-token reply. If a made-up token draws a 4xx, a bot gets past the check. Requirement 25.1 says a bad token gets the 422. Requirement 25.3 lets a check through only when Cloudflare can't be reached, gives a server error or times out.
- Read the JSON whatever the status.
- If `success` is `false`, use the error codes as now.
- Give `unreachable` only for a status of 500 or more, a body that can't be read, or a reply without a true/false `success`.
- Make the same edit to the design line "a non-2xx status … is unreachable".
- Tests:
  - 400 with `invalid-input-response` gives `failed`.
  - 400 with `invalid-input-secret` gives `misconfigured`.
  - 503 with an HTML body still gives `unreachable`.

## V60. Only one key set: say so at startup
With only one key set, the check stays off with no message, so an owner who pastes one key sees no change. When exactly one of `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` is set, log one startup warning that names the missing key, with no value: "The human check is off: TURNSTILE_SECRET_KEY is not set." Test it, including that no value appears.

## V61. Put the "couldn't confirm" message next to the widget
The message shows at the top of the form (grade-html.js 112), but the design puts it next to the widget, at the bottom near the button. On a phone, the owner may not see the top of the form after the page reloads. Show it right above the widget when it comes from the human check. Other form errors stay where they are. Test it.

## V62. Send Cloudflare the plain IPv4 address
